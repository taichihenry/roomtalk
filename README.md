# RoomTalk · 约定口令即房间

两个人（或任意多对）提前约定一个口令，各自打开同一个网址、输入这个口令，就进到同一间房，
开始文字 / 语音 / 视频通话。**不需要注册、不需要交换手机号或社交账号。**

线上地址：**https://8.中国**（`www.8.中国`、繁体 `8.中國` 会自动 301 归一过去）

---

## 一、它凭什么"不留痕迹"

| 项 | 做法 |
|---|---|
| 服务器知道口令吗 | **不知道**。浏览器里 PBKDF2-SHA256（10 万次迭代）把口令派生成 32 位十六进制房间号，只有这个派生值上传 |
| 消息会被存吗 | **不会**。Durable Object 全程不调用 storage，没有任何落库动作 |
| 通话内容服务器看得到吗 | **看不到**。文字走 WebRTC DataChannel、音视频走 SRTP，都是两端浏览器之间的加密直连 |
| 服务器到底做了什么 | 只当"介绍人"：把双方的 SDP / ICE 候选互相递一次，递完就没事了 |

```
   用户 A 的浏览器  ←──── 音视频：端到端加密直连（不过服务器）────→  用户 B 的浏览器
          │                                                              │
          └────────→  Cloudflare 边缘 · Durable Object  ←───────────────┘
                        只转发信令，一次通话总共几 KB
```

## 二、口令撞车怎么办

口令是双方私下的共享秘密，密码学上**无法区分"知道同一个口令的另一个人"和"对的人"**。
所以产品层面用三个机制兜住，而不是假装能认证：

1. **房间上限 2**。第三人拿同一个口令进来会被明确拒绝，并给出两条出路：
   「要么等他们结束后再试，要么和对方换一个更独特的口令。」
2. **设备记忆（TOFU，信任首次使用）**。第一次通话会明确标注「这是和这台设备的第一次通话，
   已记住它。」——**不假装已经认证过**。以后再进来若还是同一台设备，显示「已确认为熟悉的设备」；
   若是另一台，显示警告。
3. **一键请出 + 自动拉黑**。身份提示条上的「请出房间」在任何状态下都可达（包括已确认之后）。
   被请出的设备会被记进本地黑名单，下次再进来自动请走。

## 四、开发 / 测试 / 部署

```bash
# 本地起服务（前端 + Worker + DO，端口 8787）
cd cloudflare && npx wrangler dev

# 只测 DO 的信令逻辑，秒级返回，不用起服务
node cloudflare/test/do-sim.js

# 端到端测（需要上一步的 wrangler dev 在跑）
node test/e2e.mjs

# 部署
cd cloudflare && npx wrangler deploy
```

⚠ **本机跑 wrangler 前必须先设代理**，否则连不上 Cloudflare：

```bash
export http_proxy=http://127.0.0.1:<当前端口> https_proxy=http://127.0.0.1:<当前端口>
```

⚠ 代理会**间歇性抖**（`timed out` / `CONNECT tunnel failed, response 502`），
**循环重试 2~3 次必过**，不用改配置。

### 推送到 GitHub 即自动上线

仓库：**https://github.com/taichihenry/roomtalk**（public，`main`）。
Cloudflare 侧用 **Workers Builds** 的 Git 集成监听它，push 到 `main` 就自动构建 + 部署。

构建配置（控制台：Workers & Pages → roomtalk → Settings → Builds → Connect）：

| 设置项 | 值 | 为什么这么填 |
|---|---|---|
| Git 分支 | `main` | |
| 构建命令 | `npm ci` | 按 lock 装上锁定版本的 wrangler，别让 CI 每次去抓最新版 |
| 部署命令 | `npx wrangler deploy` | 默认值，不用改 |
| 根目录 | `cloudflare` | ⚠ 见下 |

⚠ **根目录必须填 `cloudflare`，不能留空。** 本仓库是前后端同仓，`wrangler.toml`
在 `cloudflare/` 下；留空的话 wrangler 在仓库根找不到配置，会触发它的「自动配置」
流程并给你开一个 PR —— 那不是我们要的。填了 `cloudflare` 之后，配置里的
`[assets] directory = "../public"` 从该目录解析，正好指到仓库里的 `public/`。

⚠ **Durable Object 的 Worker 不生成预览 URL**（Cloudflare 明确说明）。
所以非生产分支的构建只有校验价值，没有可点的预览地址。不在意的话可以在设置里
只保留生产分支，省构建时长。

⚠ **接上 Git 集成后不要再手动 `wrangler deploy`。** 手动部署本身能成功，
但下一次 push 触发的构建会把版本覆盖回去，容易误判成"我改的东西没上去"。
紧急绕过 CI 时手动部署仍然可用，只是记得随后补一次 push 让两端对齐。

> 依赖 lock 里的下载地址已统一为官方 `registry.npmjs.org`（不用 `npmmirror`），
> 避免海外构建环境去拉国内镜像。

**这条链路是验证过的**，不是照文档抄的：把仓库克隆到空目录，模拟 CI 做
`npm ci` → `wrangler deploy --dry-run`，产物 **13.80 KiB / gzip 5.16 KiB**
与线上一致，`../public` 正确读到 4 个文件。CI 与本地是同一套路径解析，
这一步过了就不会卡在构建上。

> Cloudflare 的 Git 集成用的是「Cloudflare Workers and Pages」这个 GitHub App。
> 本账号此前接过 Pages 项目（`cftest`），**App 安装已存在**，
> 但如果 `roomtalk` 没出现在仓库下拉列表里，去
> GitHub → Settings → Applications → Cloudflare Workers and Pages → Configure →
> Repository access，把这个仓库勾上即可。

## 五、免费额度够用吗

结论：**视频通话不花 Cloudflare 一分钱**，因为音视频是 P2P 直连，根本不经过服务器。
被消耗的只有信令，而信令极小。

| 项目 | 免费额度 | 我们的用途 |
|---|---|---|
| Workers 请求 | 100,000 / 天 | 打开页面 1 次 + 建连 1 次 |
| 带宽 / 出口流量 | **不收费** | —— |
| 静态资源请求 | **免费且不限量** | 首屏三个文件全免 |
| DO 请求 | 100,000 / 天 | 建连 1 次；收到的 WS 消息 **20 条折 1 次** |
| DO 时长 | 13,000 GB-s/天 ≈ **28.9 实例小时/天** | 只在"醒来处理消息"时计 |
| DO 存储 | 5 GB | 完全不用 storage，恒为 0 |

一次 1 小时视频通话（2 人全程在线）的消耗：

| 环节 | 计入额度 |
|---|---|
| 页面打开 | 2 次 Worker 请求（资源不计） |
| 建 WebSocket | 2 次 Worker + 2 次 DO 请求 |
| 建连信令（join / offer / answer / ICE） | 约 10~40 条 → 0.5~2 次 |
| 聊天 + 开关摄像头 | 约 20 条 → 1 次 |
| 保活 ping（25 秒 × 2 人 × 1 小时 = 288 条） | auto-response 处理，**不计费** |
| **合计** | **约 3~5 次 DO 请求 / 通话** |

即使按最悲观口径（保活 ping 也照 20:1 计费）也只有约 18 次，
换算下来仍是**每天 5,500 次一小时通话**的下限。

**并发不是瓶颈**：官方原话是「单实例 DO 可作为 WebSocket 服务端连接数千个客户端」，
而每对用户每分钟只产生约 5 条消息。稳定 24 小时不间断跑，约 **100~200 对同时通话**。

### ⚠ 唯一会让成本真的爆炸的东西：TURN 中继

现在**没有 TURN**。好处是零成本，代价是 **P2P 打不通就通不了话**
（双方都在对称 NAT、企业防火墙、部分移动网络后时）。

一旦为了兼容性加上 TURN，媒体就开始真的走服务器：

- Cloudflare Realtime TURN：**$0.05 / GB 出站，每月前 1,000 GB 免费**
- 1 小时 720p 双向 ≈ 1.8 GB → 1,000 GB ≈ **550 通话小时/月（约 18 小时/天）**
- 超了就是钱：100 小时 720p ≈ 180 GB ≈ **$9**
- **官方明写 Cloudflare 的 TURN 不走中国网络**，国内用户会被解析到境外节点，
  延迟和成功率都要打折。要覆盖国内用户，TURN 得自建 —— 这时
  render.com 免费层 100 GB/月出口只够约 55 小时 720p，是个硬顶。

另外：**Cloudflare 服务条款不允许把 Workers 当中继视频/大文件的通道**。
所以不要试图"用 Worker 转发音视频来绕过 P2P 限制"——现在的架构正好不碰这条线。

## 六、画质档位：让用户自己选

视频流量消耗的是**双方自己的手机流量**（720p 不限速约 1.4 GB/人/小时），
所以要省流量得从编码参数下手。工具栏上有一个下拉框，通话中**随时可换**：

| 档位 | 码率上限 | 编码分辨率（从 720p 采集压） | 每人每小时 |
|---|---|---|---|
| 省流量 | 300 kbps | 640×360 | 约 270 MB |
| **流畅（默认）** | 600 kbps | 947×533 | 约 540 MB |
| 清晰 | 1.2 Mbps | 1280×720 | 约 1.05 GB |

选择存在本机（`localStorage`），下次打开还是这一档。

### 为什么这样切档是「即时」的

关键在 `scaleResolutionDownBy` —— 它改的是**编码器输入**，不是摄像头。
所以切档走的是 `RTCRtpSender.setParameters()`，**不需要重新协商 SDP、
也不会重启摄像头**：一次调用，下一帧就是新档位，画面不会黑。

> 如果换成重新 `getUserMedia` 来改分辨率，每次切档画面都会黑一下 ——
> 那才叫不流畅。这是设计上刻意避开的路。

### 两个参数各管什么

| 参数 | 作用 |
|---|---|
| `maxBitrate` | 管住"不把上行打满"。**卡顿的真实根因是上行拥塞，不是画质不够** |
| `degradationPreference: 'maintain-framerate'` | 带宽不够时**降分辨率、保帧数**，画面持续流动而不是变幻灯片 |
| `scaleResolutionDownBy` | 编码前缩放，决定这一档实际输出的分辨率 |

采集端固定 720p，往下的分辨率全交给 `scaleResolutionDownBy` 压 ——
这样"清晰"档才不会被采集上限锁死，切档也才能瞬时生效。

### 一个容易被误解的点

档位决定的是**"我发出去的"画面**：调低省的是**自己手机的流量**，
对方看到的画面跟着变。反过来不成立 —— 调高**不会**让对方发得更清晰。

所以切档时会弹一句明确说明，并且顺手把自己的档位同步给对方
（对方那边会看到"对方把画质调成了「省流量」"），免得他以为是自己这边出了问题。

## 七、踩过的坑（改代码前先读）

### 部署 / 配置

- **首页必须 `run_worker_first`**。Assets 默认"静态资源优先"：`/` 命中 `index.html`
  就**根本不执行 Worker**，域名的 www / 繁体归一逻辑会静默失效。
  而 `/healthz` 没有对应文件所以能正常 301 —— 这个差异是排查时的突破口。
- **`_headers` 里只能用 `#` 注释**。写块注释 `/* */` 会被当成路径匹配符，
  后面所有规则解析失败 —— **只报 warning、不影响启动**，规则却全部静默失效。
- **静态资源是"具体的规则覆盖一般的"**，所以 `/app.js` 的缓存策略要写在 `/*` 之后。
- 国际化域名有坑：`new URL().hostname` 返回 punycode 还是 Unicode 属于实现细节，
  所以 `.xn--fiqz9s` 和 `.中國` **两种写法都要判**，只判一种会静默不跳转。
- 绑自定义域名时，DNS 面板提示"缺少 A / CNAME / MX"对 Worker 站点是**误报，一律忽略**。

### Durable Object

- **必须用 Hibernation API**（`ctx.acceptWebSocket`）。用普通 `accept()` 会让 DO
  在整条连接存活期间持续计 duration —— 单个 128MB 实例常驻一天就是 10,800 GB-s，
  而免费额度只有 13,000 GB-s/天。代价是内存状态休眠后丢失，房间表必须能**懒重建**。
- **`setWebSocketAutoResponse` 的匹配是逐字精确的字符串比较**。
  差一个空格就静默失效：不报错、功能正常，只是开始按满额计费。
- **绝不能加 `setInterval` 心跳** —— 那会不停唤醒 DO，把休眠优化彻底抵消。
- **`deserializeAttachment()` 要当深拷贝对待**。真实 DO 每次返回新对象；
  改了却不写回 `serializeAttachment`，线上会**静默丢状态**。离线测试的 shim 也必须深拷贝，
  否则浅拷贝的假 shim 永远测不出这个问题。

### 客户端

- **重连要双保险**。`onclose` 在 workerd 下可能要 10 秒以上才触发，
  所以额外用 pong 超时（8 秒）主动判定连接已死，两条路都汇总到 `handleSocketLost()`。
- 同一 `clientId` 重复进房时，服务端会**把旧连接踢掉**再放新的进来 ——
  这是网络假死重连的自愈路径。
- `--no-proxy-server` 会让本机这份 Chrome（153）**启动即退且不报错**，
  调试端口根本不监听。测试里不要加这个参数。

## 八、排障入口

页面加载后，控制台里有一个只读诊断对象 `window.__rt`（**不暴露口令**）：

```js
__rt.room                 // 房间号（口令的派生值）
__rt.connectionState      // PC 连接状态
__rt.media                // 本端 音/视频 开关
__rt.remoteMedia          // 对端 音/视频 开关
__rt.videoTuned           // 视频码率参数是否已生效
__rt.quality              // 我当前选的画质档位
__rt.remoteQuality        // 对方选的档位
await __rt.videoStats()   // 档位 / 码率上限 / 缩放 / 降级偏好 / 采集分辨率 / 实测 fps / 受限原因
__rt.__dropSocket()       // 模拟"连接已死"，验证重连
```

`videoStats().qualityLimitation` 是**把"卡"归因**的关键字段：

- `none` —— 没受限，卡顿来自网络丢包或对端
- `bandwidth` —— 带宽不够，降码率 / 降分辨率是正解
- `cpu` —— 编码算力不够，**降码率没用**，得降分辨率或帧率

没有这个字段，调码率全靠猜。
