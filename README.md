# RoomTalk · 约定口令即房间

两个人（或任意多对）提前约定一个口令，各自打开同一个网址、输入这个口令，就进到同一间房，
开始文字 / 语音 / 视频通话。**不需要注册、不需要交换手机号或社交账号。**

线上地址：**https://8.中国**（`www.8.中国`、繁体 `8.中國` 会自动 301 归一过去）

---

## 一、它凭什么"不留痕迹"

| 项 | 做法 |
|---|---|
| 服务器知道口令吗 | **不知道**。浏览器里 PBKDF2-SHA256（10 万次迭代）把口令派生成 32 位十六进制房间号，只有这个派生值上传 |
| 消息会被存吗 | **不会**。Durable Object 全程不调用 storage，没有任何落库动作 |
| 通话内容服务器看得到吗 | **看不到**。文字走 WebRTC DataChannel、音视频走 SRTP，都是两端浏览器之间的加密直连 |
| 服务器到底做了什么 | 只当"介绍人"：把双方的 SDP / ICE 候选互相递一次，递完就没事了 |

```
   用户 A 的浏览器  ←──── 音视频：端到端加密直连（不过服务器）────→  用户 B 的浏览器
          │                                                              │
          └────────→  Cloudflare 边缘 · Durable Object  ←───────────────┘
                        只转发信令，一次通话总共几 KB
```

## 二、口令撞车怎么办

口令是双方私下的共享秘密，密码学上**无法区分"知道同一个口令的另一个人"和"对的人"**。
所以产品层面用四个机制兜住，而不是假装能认证：

1. **房间上限 2**。第三人拿同一个口令进来会被明确拒绝，并给出两条出路：
   「要么等他们结束后再试，要么和对方换一个更独特的口令。」
2. **设备名条**。每台设备进房时自动报上自己是什么设备（`Android · Pixel 8` / `iPhone` /
   `Windows 电脑`…），界面上常驻一行「我 / 对方」各是什么。口令分不清人，
   但一句「你那边显示的是什么？」就能对上 —— 这是纯口令方案能拿到的最便宜的一道确认。
   安卓的真实机型属于 UA-CH 的高熵字段，只能异步取，拿到后会补报一次（rename）。
3. **设备记忆（需要用户点头，不自动记住）**。第一次通话会明确标注「这是和这台设备的第一次通话」，
   并把「记住这台设备」交给用户点一下 —— **不替用户做这个决定，也不假装已经认证过**。
   > 为什么首访不自动记住：口令是共享秘密，谁先拿到谁先进。自动信任等于把「先到的那个
   > 陌生人」永久写成「已确认」，真正的对方反而成了「设备换过」的可疑对象。
   > 这是最糟的信任模型 —— TOFU 也得分用户点头的那一步。

   点过之后，同一台设备再进来显示「已确认为熟悉的设备」；换了一台则显示警告。
4. **一键请出（仅房主）+ 可开关的自动请出**。口令是共享秘密，谁拿到都能进；房间上限是 2，
   一旦被陌生人占了位子，真正的对端就进不来。所以「请出房间」这道口子必须留着 ——
   但权限**只给房主**。后进来的一方看不到这个按钮，也没有这个权限
   （服务端 `_handleKick` 会独立校验，前端藏按钮不算数）。

### 房主规则：谁先退出谁让位

房主 = **第一个进入这间房的人**。身份记在每个成员的 attachment 上
（`roomHost[房间号] = 房主的身份键`），所以不额外维护内存表，休眠重建后也不会丢。

| 事件 | 结果 |
|---|---|
| 第一个进房 | 成为房主，拥有「请出房间」权限 |
| 后进者 | 没有按钮、没有权限，服务端会拒绝他的踢人请求 |
| 房主退出、房里还有人 | 剩下的人**立刻**接任房主（收到 `host` 消息），**房间不关闭** |
| 原房主再进来 | 是**后进者**，自动失去请出权限 |
| 两人都退出 | 房间（也就是这个口令的占用）才真正腾空 |
| 腾空后谁先开房 | 谁成为新房主，可请出后来的人 |

刻意**不做**「原房主回来就把身份还给他」：规则简单、确定、能对用户解释清楚；
而「两个人争房主」是没法解释的。代价是刷新页面也会让位。

> 断线（TCP 假死、切基站）走的是同一条路：`webSocketClose → _leave → _ensureHost`，
> 同样立刻移交。所以网络抖一下，房里剩下的人就会当上房主。

### 「自动请出」开关（房主专属）

手滑点错「请出房间」是个真实会翻车的场景：对方被记进本地黑名单，之后再进来自动被请走 ——
**房主就永远等不到对方了**，退出重进都没用（黑名单在 `localStorage`）。

所以把「自动 / 手动」交给房主自己定：

- **自动（默认）**：拉黑过的设备一进来就请走。口令被陌生人猜到时的防线。
- **手动**：只提示、不动手，由房主看着办 —— 误请之后用它把人放回来。
- 另有「解除拉黑」按钮（名单非空时才出现），把名单整个清掉，彻底回到没拉黑过的状态。

开关是**设备级的个人偏好**（`localStorage: rt.autokick`），不按房间存。

```bash
# 本地起服务（前端 + Worker + DO，端口 8787）
cd cloudflare && npx wrangler dev

# 只测 DO 的信令逻辑，秒级返回，不用起服务
node cloudflare/test/do-sim.js

# 只测 Worker 入口的「协议 + 域名归一」，也不用起服务
node cloudflare/test/redirect.js

# 端到端测（需要上一步的 wrangler dev 在跑）
# 会顺手把全屏视频区两个状态截图留档：docs/shot-call-remote.png（对方铺满 + 我小窗，默认）、
# docs/shot-call-self.png（点过我那格之后）—— 给人眼复核用，不参与断言
node test/e2e.mjs

# 部署
cd cloudflare && npx wrangler deploy
```

⚠ **本机跑 wrangler 前必须先设代理**，否则连不上 Cloudflare：

```bash
export http_proxy=http://127.0.0.1:<当前端口> https_proxy=http://127.0.0.1:<当前端口>
```

（`npm ci` 也一样 —— lock 里指向官方 `registry.npmjs.org`，不走镜像。
只是为了对齐 CI，本地临时救急可以用
`npm ci --registry=https://registry.npmmirror.com`。）

⚠ 代理会**间歇性抖**（`timed out` / `CONNECT tunnel failed, response 502`），
**循环重试 2~3 次必过**，不用改配置。

### 推送到 GitHub 即自动上线

仓库：**https://github.com/taichihenry/roomtalk**（public，`main`）。
Cloudflare 侧用 **Workers Builds** 的 Git 集成监听它，push 到 `main` 就自动构建 + 部署。

> ⚠ **本项目要走「连接已存在的 Worker」，不能走「从仓库新建」。**
> `roomtalk` 这个 Worker 早就部署过，`8.中国` 的四条自定义域名都挂在它上面。
> 正确入口是 **点进 roomtalk → Settings → Builds → Connect**。
> 首页的 *Create application → Import a repository* 那条路是**新建 Worker** 用的，
> 拿它接本仓库会撞上已存在的 `roomtalk` 名字。（flashdrop 当初是从零开始，所以走的是那条。）

构建配置（控制台：Workers & Pages → roomtalk → Settings → Builds → Connect）：

| 设置项 | 值 | 为什么这么填 |
|---|---|---|
| Git 分支 | `main` | |
| 构建命令 | `npm ci` | 按 lock 装上锁定版本的 wrangler，别让 CI 每次去抓最新版 |
| 部署命令 | `npx wrangler deploy` | 默认值，不用改 |
| 根目录 | `cloudflare` | ⚠ 见下 |

⚠ **根目录必须填 `cloudflare`，不能留空。** 本仓库是前后端同仓，`wrangler.toml`
在 `cloudflare/` 下；留空的话 wrangler 在仓库根找不到配置，会触发它的「自动配置」
流程并给你开一个 PR —— 那不是我们要的。填了 `cloudflare` 之后，配置里的
`[assets] directory = "../public"` 从该目录解析，正好指到仓库里的 `public/`。

⚠ **Worker 名必须和配置里的 `name` 一致。** 官方明确：面板里的 Worker 名与指定根目录下
`wrangler.toml` 的 `name` 对不上时，**构建会直接失败**。本项目两边都是 `roomtalk`，
天然满足；但以后若要改名，必须两边同时改。

⚠ **Durable Object 的 Worker 不生成预览 URL**（Cloudflare 明确说明）。
所以非生产分支的构建只有校验价值，没有可点的预览地址。不在意的话可以在设置里
只保留生产分支，省构建时长。

⚠ **接上 Git 集成后不要再手动 `wrangler deploy`。** 手动部署本身能成功，
但下一次 push 触发的构建会把版本覆盖回去，容易误判成"我改的东西没上去"。
紧急绕过 CI 时手动部署仍然可用，只是记得随后补一次 push 让两端对齐。

> **额度**：Workers Builds 免费计划 **3,000 构建分钟/月**。本项目一次构建约 1 分钟，
> 一个月能推上千次；用完之后只是"构建排队不动了"，**不会自动扣费**。

> 依赖 lock 里的下载地址已统一为官方 `registry.npmjs.org`（不用 `npmmirror`），
> 避免海外构建环境去拉国内镜像。

**这条链路是验证过的**，不是照文档抄的：把仓库克隆到空目录，模拟 CI 做
`npm ci` → `wrangler deploy --dry-run`，产物 **13.80 KiB / gzip 5.16 KiB**
与线上一致，`../public` 正确读到 4 个文件。CI 与本地是同一套路径解析，
这一步过了就不会卡在构建上。

> Cloudflare 的 Git 集成用的是「Cloudflare Workers and Pages」这个 GitHub App。
> 本账号此前接过 Pages 项目（`cftest`），**App 安装已存在**，
> 但如果 `roomtalk` 没出现在仓库下拉列表里，去
> GitHub → Settings → Applications → Cloudflare Workers and Pages → Configure →
> Repository access，把这个仓库勾上即可。

#### ⚠ 排查：push 成功了，但 Cloudflare 没有任何构建

**症状**：`git push` 返回成功，但部署记录里没有新条目，线上还是旧版本。
这个坑 2026-10-07 真实踩过一次，**花了一个多小时才定位**，照下面顺序查能省时间。

**根因（最常见）**：GitHub 侧的 `Cloudflare Workers and Pages` App 被卸载/失效了，
但 **Cloudflare 面板里仍显示"已连接 `taichihenry/roomtalk`"** —— 那是个**孤儿引用**。
push 产生的 webhook 无处投递，构建永远不会被触发。
面板上还常常挂一条横幅：
`There is an internal issue with your Cloudflare ... Git installation`。

**第一步永远是**：浏览器打开 👉 `https://github.com/settings/installations`
（或 **Settings → Applications → Installed GitHub Apps**），
看 **`Cloudflare Workers and Pages` 在不在**。
- **不在** → 就是它。去 `https://github.com/apps/cloudflare-workers-and-pages` → **Install**
  → 选账户 → 勾仓库 → Install。
- **在** → 继续往下查（见"其他可能"）。

**修好后必须回 Cloudflare 重连**：因为安装是**账号级**的，重装不会自动修复已存的项目引用。
进 **roomtalk → Settings → Builds**，先点 **「断开连接」**，再点 **「连接」**，
重新选账户 / 仓库，表单按上表重填一遍。

**⚠ 这一步每个项目都要各自做一次。** 同一个 app 下的**所有** Workers/Pages
（本账号还有 `flashdrop`）都要回去"断开 → 重连"，**不会**因为修好了 roomtalk 就自动都好。

**最快的验证方式**（不用翻控制台）：
```bash
gh api repos/taichihenry/roomtalk/commits/main/check-runs \
  --jq '.check_runs[] | .name + " → " + (.conclusion // .status)'
```
构建触发后会有一条名为 **`Workers Builds: roomtalk`** 的 check-run
（`queued → in_progress → success`）。
> 这点值得记一下：早期以为"Cloudflare 构建不在 GitHub 侧留痕"，**是错的** ——
> **Worker 项目**的构建会正常发 check-run，`gh` 一条命令就能看状态，比登控制台快得多。

**其他可能**（check-run 出现了但仍失败）：
| 现象 | 原因 |
|---|---|
| 冒出个自动配置 PR / 报找不到配置 | **根目录没填 `cloudflare`** |
| 构建报 Worker 名不匹配 | 接错了项目，或根目录不对 |
| `npm ci` 阶段挂 | 依赖装不上（检查 lock 的源） |
| 部署阶段报鉴权失败 | Builds 令牌权限不够 → 表单里把 API 令牌改成「创建新令牌」 |

> 兜底方案：若重装后横幅仍在（社区确有此类，需提工单让 Cloudflare 后台重置），
> 改用 **GitHub Actions + `cloudflare/wrangler-action`**，自己在面板建 API Token 存进
> repo secret，由 Actions 跑 `wrangler deploy`，**完全绕开 Cloudflare 的 Git 集成**。

## 五、免费额度够用吗

结论：**视频通话不花 Cloudflare 一分钱**，因为音视频是 P2P 直连，根本不经过服务器。
被消耗的只有信令，而信令极小。

| 项目 | 免费额度 | 我们的用途 |
|---|---|---|
| Workers 请求 | 100,000 / 天 | 打开页面 1 次 + 建连 1 次 |
| 带宽 / 出口流量 | **不收费** | —— |
| 静态资源请求 | **免费且不限量** | 首屏三个文件全免 |
| DO 请求 | 100,000 / 天 | 建连 1 次；收到的 WS 消息 **20 条折 1 次** |
| DO 时长 | 13,000 GB-s/天 ≈ **28.9 实例小时/天** | 只在"醒来处理消息"时计 |
| DO 存储 | 5 GB | 完全不用 storage，恒为 0 |

一次 1 小时视频通话（2 人全程在线）的消耗：

| 环节 | 计入额度 |
|---|---|
| 页面打开 | 2 次 Worker 请求（资源不计） |
| 建 WebSocket | 2 次 Worker + 2 次 DO 请求 |
| 建连信令（join / offer / answer / ICE） | 约 10~40 条 → 0.5~2 次 |
| 聊天 + 开关摄像头 | 约 20 条 → 1 次 |
| 保活 ping（25 秒 × 2 人 × 1 小时 = 288 条） | auto-response 处理，**不计费** |
| **合计** | **约 3~5 次 DO 请求 / 通话** |

即使按最悲观口径（保活 ping 也照 20:1 计费）也只有约 18 次，
换算下来仍是**每天 5,500 次一小时通话**的下限。

**并发不是瓶颈**：官方原话是「单实例 DO 可作为 WebSocket 服务端连接数千个客户端」，
而每对用户每分钟只产生约 5 条消息。稳定 24 小时不间断跑，约 **100~200 对同时通话**。

### ⚠ 唯一会让成本真的爆炸的东西：TURN 中继

现在**没有 TURN**。好处是零成本，代价是 **P2P 打不通就通不了话**
（双方都在对称 NAT、企业防火墙、部分移动网络后时）。

一旦为了兼容性加上 TURN，媒体就开始真的走服务器：

- Cloudflare Realtime TURN：**$0.05 / GB 出站，每月前 1,000 GB 免费**
- 1 小时 720p 双向 ≈ 1.8 GB → 1,000 GB ≈ **550 通话小时/月（约 18 小时/天）**
- 超了就是钱：100 小时 720p ≈ 180 GB ≈ **$9**
- **官方明写 Cloudflare 的 TURN 不走中国网络**，国内用户会被解析到境外节点，
  延迟和成功率都要打折。要覆盖国内用户，TURN 得自建 —— 这时
  render.com 免费层 100 GB/月出口只够约 55 小时 720p，是个硬顶。

另外：**Cloudflare 服务条款不允许把 Workers 当中继视频/大文件的通道**。
所以不要试图"用 Worker 转发音视频来绕过 P2P 限制"——现在的架构正好不碰这条线。

## 六、通话与消息：为什么必须双方各自点一下

### 「互相听不到」的三种真凶，以及各自的解法

用户反馈「有时候互相听不到对方声音」。逐个查过，其实是三件事被混在一起：

| 真凶 | 表现 | 解法 |
|---|---|---|
| **对面没开麦** | 我说话他听得到，他说话我听不到 | 视频/语音窗口角标直接写「对方 · Windows 电脑 · **未开麦**」，不用猜 |
| **浏览器拦了自动播放** | 视频在动、画面正常，就是没声音 | `video.play()` 失败时不再静默 `catch`，而是弹出「🔊 点这里打开」解锁条；界面任意一次点击也会顺手重试 |
| **得双方各自开麦** | 以为「进房就该自动通」 | 这是**设计如此**，见下 |

### 为什么要「呼叫 → 接听」

**开麦必须由使用者自己点，这是浏览器强制的，不是我们偷懒**：
`getUserMedia({audio:true})` 在没有用户手势时会被直接拒绝。

所以输入栏上的语音 / 视频两颗按钮做的是两件事：

1. **我自己这边立刻开麦 / 开镜头**（这是我的手势，合法）—— 但**只是本地预览，
   一个字节都不往外发**；
2. 给对方发一条 `ring`；**对方点「接听」的那一刻，我才开始把音视频推给他**，
   同时他那边的麦克风才开。

⚠ **「采集」和「发送」必须是两个动作，中间隔着「对方接听」。**
早先的写法是 `ensureMic/ensureCam` 一拿到轨道就 `pc.addTrack`，而发起流程又在发
`ring` **之前**就调它们 —— 于是「我按了发起」等于「我立刻开始推流」：**对方还没
接听就听得见我的声音、看得见我的画面**；我中途挂断，他那边画面还定格在最后一帧；
更糟的是他回头点一下「接听」，会接通一通早已结束的电话，而我这边甚至还能听见
他说话。对方点不点「接听」形同虚设 —— 这是实打实的隐私事故。

现在分成三道闸门（缺一不可）：

| 闸门 | 位置 | 挡住什么 |
|---|---|---|
| 采集不发送 | `ensureMic/ensureCam(publish=false)` | 呼叫期间只做本地预览，不挂进 PC |
| 发送要过闸 | `publishLocalTracks()` 开头 `if (S.callRinging) return` | 无论谁调的（切摄像头、开关麦、重连重建 PC……）都发不出去 |
| 收到也不放 | `pc.ontrack` 里 `if (!callLive()) return` | 对方的轨道到了也只攒着，接通才接进播放元素 |

第三条是**接收端的兜底**：就算对面是旧版本、或将来哪条路径又漏了，只要我还没
接听，他的画面和声音就进不了我的播放元素。

> **挂断也要收干净。** 发起方挂断时会发一条 `bye` —— 少了它，对方那块「来电浮层」
> 会一直挂着，过一会儿点「接听」还能接通一通早就结束的电话。收到 `bye` 时若还没
> 接听，要把浮层收掉、并把**这颗来电标记为作废**；接听流程里夹着
> `await getUserMedia`，回来时必须重新确认这颗来电还有效，无效就把刚开的麦克风
> 放掉。（判据存在 `S.ringGone`，因为 `bye` 到达时 `S.ringKind` 已经被清空了。）

顺带解掉一个隐蔽的坑：**对方点「接听」这个手势，同时解锁了他浏览器里远端音频的自动播放**。
不做这一步，就会出现「接了但听不到」。

> **顶栏不放假控件。** 麦克风 / 摄像头开关不放在顶栏 —— 它们在通话界面里
> （通话中才用得上），而「发起通话」在输入栏旁边。同一个动作只留一个入口。
> 顶栏只剩「连接状态 / 我发出的画质 / 离开房间」。

### 通话界面：全屏，并且顺手堵掉「重复发起」

通话一经建立（我发起或对方接听），整个房间进入 **call-mode**：

- 顶栏、设备名条、身份条、消息流、**输入栏全部收起**，屏幕交给画面；
- 上方一行是「对方是谁 + 通话时长」；下方一排圆形按钮：**静音 / 关摄像头 / 翻转 / 挂断**
  （挂断红底、全场最醒目）；
- 语音通话用全屏头像视图（没有视频可看，就不摆两块空窗）；视频通话用全屏舞台。

**顶栏原本还挂着一对麦克风 / 摄像头开关，现在撤掉了** —— 输入栏那两颗「发起语音通话」
「发起视频通话」按钮本就含同样的开麦开镜语义，两处并存只会让人猜「哪个才是真的」。
撤掉之后，通话中能调麦调镜的地方只剩通话界面这一排，职责唯一。
按钮图标也从 emoji 换成**内联描边 SVG**：emoji 的观感由系统字体决定（Windows 那套尤其难看），
SVG 走 `stroke="currentColor"`，状态色一改图标跟着变，且三端完全一致。

「输入栏收起」不只是视觉选择 —— 它正是**「已经在通话了，又去点发起通话」从界面上
就不成立**的原因。代码里另有一道保险（`startCall` 一进来就检查 `inCall()`），
因为自动化脚本、无障碍工具和边角时序都可能绕过界面。

通话态的判据是 `S.callKind`（`null | 'audio' | 'video'`），**不是** `S.media`：
视频通话里关掉自己的摄像头属于常事（`media.video=false`），那时当然还在通话中。
把两件事混成一个标志位，`applyStageLayout` 和界面显隐就会在「关摄像头」的那一下集体错乱。

呼叫超时 30 秒自动收摊（否则发起方会挂着一个永远不结束的「正在呼叫」）；
对方挂断走一条 `{t:'bye'}`，两边同时收媒体 —— 只收界面不停媒体，
摄像头指示灯会一直亮着。

### 对方「离开」有两种，别混为一谈

`peer-left` 带着 `reason`，客户端据此决定是「立刻收摊」还是「留宽限期等他重连」：

| reason | 什么情况 | 对端该怎么办 |
|---|---|---|
| `leave` | 对方主动点 ✕ 退房 | **立刻**收掉摄像头 —— 他不会再回来了 |
| `closed` | 连接意外断开 | 聊天态等 1.5 秒、**通话态等 20 秒**；期间他若带同一身份回来就继续通话 |

不区分的代价是两头不讨好：一律等 → 对方明明走了，你还亮着摄像头干等 20 秒；
一律不等 → 网络抖一下就把正在进行的通话掐掉。

⚠ **「主动退房」不能只靠端到端的 `bye`。** `bye` 走 DataChannel 的 `send()`，而那是
**排队**的；退房时紧接着就 `teardownPeer()` 把连接拆了，那条 bye 经常还没出网就被丢掉
（表现：对方退房了，你却一直停在通话界面）。可靠的信号是**服务端在 `peer-left` 上带的
`reason`** —— 它走 WS，且「先发消息、再关连接」，顺序有保证。`bye` 仍然保留：
它更快，送到了就是白赚的一跳。

⚠ 另一半是**通话态的宽限期必须给足 20 秒**，这在本地测不出来 —— 线上重连要走
「退避 + WS 握手 + 重新注册」，远超 1.5 秒；而本地 `wrangler dev` 在同进程里几十
毫秒就重连完。所以这个毛病**本地永远绿、线上必现**。它的来龙去脉见
`PEER_LEFT_GRACE_CALL` 的注释，以及第八节那条「信令抖 ≠ 通话断」。

### 消息：文字 / 语音 / 文件

三种都走同一条 DataChannel（端到端，服务器不经手）：

| 类型 | 怎么发 | 说明 |
|---|---|---|
| 文字 | 输入框回车 | |
| 语音 | 切到话筒模式，**按住那颗大圆按钮说话、松手发送** | MediaRecorder 录制，最长 60 秒；短于 0.5 秒算误触，自动丢弃 |
| 文件 | 📎 选文件 | 单文件上限 100MB，多选可一次发多个 |

> 「按住说话」刻意做成一枚**居中的大圆按钮**（62px，窄屏 58px），不是扁平长条。
> 长条看着好按，实际拇指一滑就出界、`pointerup` 收不到，表现就是「按住了却松不开」
> ——这正是用户报的「经常无法持续按住触发」。同时把 `contextmenu` 也拦掉
> （iOS 会选中文字、Android 会弹菜单，都会打断按住不放）。

分片协议是三段式的：`{xfer,begin}` → 若干 `ArrayBuffer` 分片 → `{xfer,end}`。
`chat` 通道是 `ordered: true`，二进制必然落在 begin 和 end 之间，
所以接收端只要一个「当前正在收的传输」状态机就够了，**不需要序号**。

⚠ **背压必须自己做**：DataChannel 的缓冲没有上限保护，连着 `dc.send` 几十 MB
会瞬间把 `bufferedAmount` 顶爆然后抛错。所以按 16KB 切片，
`bufferedAmount > 1MB` 就等 `bufferedamountlow` 再继续。

> 收到的语音 / 文件只存在内存里（`Blob`），**不落盘、刷新即失** ——
> 这和「消息不存储」是同一条边界。文件一律给一个 `<a download>`，
> 由用户自己决定要不要存，不做「自动打开」这种喧宾夺主的事。

### 视频区：默认就是微信那个样子（对方铺满 + 我小窗）

这里前后改过两轮，把两件事合起来才是最终形态：

- 第一版是「对方铺满 + 自己缩在右下角 26%」，但舞台固定宽高比 + `object-fit: cover`，
  **对方的竖屏画面被硬裁一大块**（用户原话：「显示不全，像被局部放大」）；
- 第二版为了止损改成「两块等分 + contain」，裁切是没了，但视频通话最自然的
  「看对方」这件事被对称布局冲淡了。

现在：

- **默认就是对方铺满、我缩在右上角小窗** —— 微信视频通话的观感，也是通话里最自然的默认；
- 大窗**一律 `object-fit: contain`**：宁可留黑边也不裁切。「看得见整个人」比
  「填满每一像素」重要得多；
- **小窗改用 `cover`**：缩略图只有巴掌大，那圈黑边会让画面小到什么都看不清，宁可轻微裁一点；
- **点任意一格就互换**（微信也这样）：点小窗 → 我铺满、对方缩小窗；再点换回来。
  两端各点各的、互不干扰 —— 布局是本地选择，不会通过信令去改对方屏幕；
- 自己那格水平镜像（像照镜子），角标写「我 · 设备名」，对方那格写「对方 · 设备名 · 未开麦」；
- 舞台在通话态是 `position: fixed; inset: 0` 全屏铺满（见上一节），小窗固定右上角
  `width: 32%`、上限 150px；`.pane` 是 `role="button"` + `tabindex="0"`，
  Enter / 空格也能切 —— 不让键盘用户点得动，那就是个假按钮。

⚠ **「用户点过」和「程序自动摆」必须分开记。** `stageMain` 一个变量扛不住两件事：
挂断再接通时它会被清空，若只看它，下一次 `remoteMedia` 变化（对方开关摄像头）
又会把布局盖回去，用户刚点的那一下白点了。所以另加 `S.stagePicked` ——
**用户亲手点过就永久保留他的选择，直到这通电话结束**（`stopLocalMedia()` 才复位）。

⚠ **对方画面还没到时不摆空屏**：`applyStageLayout` 若发现对方视频轨还没来，
先把自己铺满（否则整屏是黑的），等对方画面到了再自动让位；这只在 `stagePicked` 为假时发生。

`fitStage()` 在通话态直接 `return` —— 全屏舞台不需要再按画面比例算高度，
那个 62% 上限只服务于「聊天气泡 + 内嵌视频条」的旧形态。

### 前后摄像头切换

那个 🔄 出现在**全屏通话界面的按钮排**里（顶栏不放控件了），且只在两件事同时成立时才露：
**① 正在视频通话中**（`S.callKind === 'video'`）**② `enumerateDevices` 探到 ≥2 颗摄像头**。
桌面单摄笔记本上不露 —— 露出来只会让人白点一次，再收到一句失败提示（`refreshCamCount()`）。

- 换轨走 `RTCRtpSender.replaceTrack()`：**不重新协商、不断流、画面不黑**；
- 换完立刻 `stop()` 旧轨道。**这条最不能省**：不 stop，摄像头指示灯会一直亮着，
  用户会以为被偷拍 —— 这个信任代价付不起；
- 取新轨道分两步：先按 `facingMode: { exact }` 要（语义最准），不认 facingMode
  的机型再从 `enumerateDevices` 里按 `deviceId` 挑「另一颗」；
- **镜像跟着朝向走**：前置镜像（照镜子），后置不镜像（否则拍到的字是反的）；
- 中途失败会把已经拿到手的新轨道 `stop()` 掉再抛错 —— 否则那条轨道悬着，灯一样灭不了。

#### ⚠ 手机上必须「先关旧的，再开新的」

**绝大多数手机没法同时打开前后两颗摄像头**（camera2 并发只在部分 Android 11+ 机型上
可用，iOS 从来不给）。桌面可以「先把新流拿到手，再关旧的」，手机这样干，第二次
`getUserMedia` 会直接抛 `NotReadableError`（资源被占）——**切换必然失败**。

所以 `flipCamera()` 走两阶段：

| 阶段 | 做什么 | 谁会走这条 |
|---|---|---|
| **A** | 不动现有画面，直接要新轨道 | 桌面、支持双开的机型 —— **全程没有一帧黑屏** |
| **B** | A 失败**且错误是「设备忙/读不到」**时，先 `stop()` 旧轨、等 240 ms 让硬件释放，再要一次 | 绝大多数手机 |
| 失败 | **回滚**：把原朝向重新打开，绝不把用户丢在黑屏上 | 两颗都拿不到时 |

单摄设备**不会**走进 B —— 它报的是 `OverconstrainedError`（根本没这颗镜头）而不是
「忙」，所以现有画面一点没动，直接提示「没有另一颗摄像头」就收工，不会白闪一下摄像头灯。

另一个坑：`deviceId` 排除不严会**「换到自己」**。`excludeId` 取
`getSettings().deviceId`，某些机型返回空，此时 `others` 变成全集、`others[0]` 可能
正是当前那颗 —— 画面没变，用户同样判定为「点了没反应」。所以 `deviceId` 空时退用
`label` 排除，**两者都拿不到就宁可明确报失败，也不瞎取一颗**。

失败提示按错误码分化（`camErrText()`），不再一律说「可能只有一颗摄像头」——
`NotReadableError` 会说「摄像头被占用，请关掉相机、微信等再用」，用户才知道该怎么办。
排障看 `__rt.flipLog`（最近一次切换的步骤轨迹，手机上出问题时报这个最快）。

## 七、画质档位：让用户自己选

视频流量消耗的是**双方自己的手机流量**（720p 不限速约 1.4 GB/人/小时），
所以要省流量得从编码参数下手。工具栏上有一个下拉框，通话中**随时可换**：

| 档位 | 码率上限 | 编码分辨率（从 720p 采集压） | 每人每小时 |
|---|---|---|---|
| 省流量 | 300 kbps | 640×360 | 约 270 MB |
| **流畅（默认）** | 600 kbps | 947×533 | 约 540 MB |
| 清晰 | 1.2 Mbps | 1280×720 | 约 1.05 GB |

选择存在本机（`localStorage`），下次打开还是这一档。

### 为什么这样切档是「即时」的

关键在 `scaleResolutionDownBy` —— 它改的是**编码器输入**，不是摄像头。
所以切档走的是 `RTCRtpSender.setParameters()`，**不需要重新协商 SDP、
也不会重启摄像头**：一次调用，下一帧就是新档位，画面不会黑。

> 如果换成重新 `getUserMedia` 来改分辨率，每次切档画面都会黑一下 ——
> 那才叫不流畅。这是设计上刻意避开的路。

### 两个参数各管什么

| 参数 | 作用 |
|---|---|
| `maxBitrate` | 管住"不把上行打满"。**卡顿的真实根因是上行拥塞，不是画质不够** |
| `degradationPreference: 'maintain-framerate'` | 带宽不够时**降分辨率、保帧数**，画面持续流动而不是变幻灯片 |
| `scaleResolutionDownBy` | 编码前缩放，决定这一档实际输出的分辨率 |

采集端固定 720p，往下的分辨率全交给 `scaleResolutionDownBy` 压 ——
这样"清晰"档才不会被采集上限锁死，切档也才能瞬时生效。

### 一个容易被误解的点

档位决定的是**"我发出去的"画面**：调低省的是**自己手机的流量**，
对方看到的画面跟着变。反过来不成立 —— 调高**不会**让对方发得更清晰。

所以切档时会弹一句明确说明，并且顺手把自己的档位同步给对方
（对方那边会看到"对方把画质调成了「省流量」"），免得他以为是自己这边出了问题。

## 八、踩过的坑（改代码前先读）

### 部署 / 配置

- **首页必须 `run_worker_first`**。Assets 默认"静态资源优先"：`/` 命中 `index.html`
  就**根本不执行 Worker**，域名的 www / 繁体归一逻辑会静默失效。
  而 `/healthz` 没有对应文件所以能正常 301 —— 这个差异是排查时的突破口。
- **`_headers` 里只能用 `#` 注释**。写块注释 `/* */` 会被当成路径匹配符，
  后面所有规则解析失败 —— **只报 warning、不影响启动**，规则却全部静默失效。
- **静态资源是"具体的规则覆盖一般的"**，所以 `/app.js` 的缓存策略要写在 `/*` 之后。
- 国际化域名有坑：`new URL().hostname` 返回 punycode 还是 Unicode 属于实现细节，
  所以 `.xn--fiqz9s` 和 `.中國` **两种写法都要判**，只判一种会静默不跳转。
- 绑自定义域名时，DNS 面板提示"缺少 A / CNAME / MX"对 Worker 站点是**误报，一律忽略**。
- **强制 https 的判别信号不能用 `cf-connecting-ip`**，也不能用 `url.hostname` / `Host` 头 ——
  `wrangler dev` 会把请求**伪装成生产域名**（routes 绑了哪个就用哪个），实测本地拿到的是
  `http://8.xn--fiqs8s/healthz`、`Host: 8.xn--fiqs8s`，**端口还被抹掉**；
  同时它会把 `cf-connecting-ip` 设成 `127.0.0.1`。
  于是「跳 https」的规则会把**本地开发和 e2e 全部 301 走**（本地地址 https 根本连不上）。
  可靠信号是只有边缘才注入的 `cf-ray` / `cf-visitor` / `x-forwarded-proto` ——
  本地实测这三个全是 null。见第十一节。

### Durable Object

- **必须用 Hibernation API**（`ctx.acceptWebSocket`）。用普通 `accept()` 会让 DO
  在整条连接存活期间持续计 duration —— 单个 128MB 实例常驻一天就是 10,800 GB-s，
  而免费额度只有 13,000 GB-s/天。代价是内存状态休眠后丢失，房间表必须能**懒重建**。
- **`setWebSocketAutoResponse` 的匹配是逐字精确的字符串比较**。
  差一个空格就静默失效：不报错、功能正常，只是开始按满额计费。
- **绝不能加 `setInterval` 心跳** —— 那会不停唤醒 DO，把休眠优化彻底抵消。
- **`deserializeAttachment()` 要当深拷贝对待**。真实 DO 每次返回新对象；
  改了却不写回 `serializeAttachment`，线上会**静默丢状态**。离线测试的 shim 也必须深拷贝，
  否则浅拷贝的假 shim 永远测不出这个问题。
- **attachment 上的字段必须"有进有出"**。`rooms` 和 `roomHost[房间号]` 是一对，
  退出房间时两个都要删。只清 `rooms` 不清 `roomHost`，一条开了一整天的连接会拖着
  几十条已退出房间的记录一路变大，最后撞上 attachment 体积上限 —— 那时 `_patch`
  会静默吞掉异常，**连还留着的房间也一起丢房主记录**。

### 客户端

- **重连要双保险**。`onclose` 在 workerd 下可能要 10 秒以上才触发，
  所以额外用 pong 超时（8 秒）主动判定连接已死，两条路都汇总到 `handleSocketLost()`。
- 同一 `clientId` 重复进房时，服务端会**把旧连接踢掉**再放新的进来 ——
  这是网络假死重连的自愈路径。
- `--no-proxy-server` 会让本机这份 Chrome（153）**启动即退且不报错**，
  调试端口根本不监听。测试里不要加这个参数。
- **`teardownPeer()` 里不能清 `S.peerName`**。它管的是「WebRTC 连接」而不是「对面是谁」，
  而且 `preparePeer()` 内部就会调它 —— 清掉的话，刚在 `peer-joined` 拿到的设备名
  会被自己立刻抹掉。对端真走了才清（`handlePeerLeft` / `kickPeer`）。
- **别拿「状态文案含『已连接』」当重连成功的判据**。断线后状态栏**不会**被清空，
  旧文案还挂在那儿，`waitUntil` 第一轮就命中，等于没等。
  可靠判据是「`peerId` 变了 **且** `dcOpen === true`」。
- **接听是异步的**（要等 `getUserMedia`）。`element.click()` 一返回就断言
  `__rt.media.audio`，拿到的一定是旧值 —— 必须 `waitUntil`。
- **按住说话要处理「松手早于麦克风就绪」**。`pointerdown` 里 `await getUserMedia`
  期间用户可能已经抬手；不判断的话录音会一直挂到 60 秒上限，
  用户会觉得「按一下就开始偷录」。（`holdWanted` 标记解决。）
- **高频事件不要直接挂重活**。`resize` 每像素触发一次，而 `fitStage()` 要读
  `clientWidth`（强制同步布局）再写 `height`（触发重排）—— 直接挂上去就是一路抖。
  统一走 `queueFitStage()`，合并到帧上、一帧最多算一次。
- **传输分片取 64KB，不是 16KB**。SCTP 单条消息上限普遍在 256KB 以上，64KB 很安全；
  而 100MB 文件的 `send` 次数从 6400 降到 1600 —— 每次 `send` 都有固定开销，
  片切得太碎会让大文件传起来发闷。
- **改了 `app.js` / `app.css` 就顺手改 `index.html` 里的 `?v=`**。静态资源缓存 10 分钟，
  不带版本号的话，上线瞬间会有用户拿到「新页面 + 旧脚本」。⚠ `preload` 的 `href`
  必须与 `<script src>` 逐字一致（含 `?v=`），否则等于白下载两份。
- **通话态与媒体态是两件事，别混用一个标志位**。视频通话里关掉自己的摄像头
  （`media.video = false`）当然还在通话中。若 `syncStage` / `applyStageLayout`
  从 `media` 反推「在不在通话」，关摄像头那一下界面就会整体错乱。
  判据只认 `S.callKind`（`null | 'audio' | 'video'`）。
- **`pushMediaState()` 在「呼叫中」必须闭嘴**。`startCall()` 里 `ensureMic()` 会顺手广播
  `{media:{audio:true}}`，可此时对方**还没接听** —— 收方一置 `remoteMedia.audio = true`，
  `applyStageLayout` 就错误地把发起方摆成大窗（屏幕先亮一块）。所以 `S.callRinging`
  时直接 `return`，等接通（`ring-answer`）再补发一次。
- **`stageMain` 一个人扛不住「用户点过」和「程序自动摆」**。挂断再接通时它会被清空，
  若只看它，之后任意一次 `remoteMedia` 变化又会把布局盖回去，用户刚点的那一下白点了。
  必须配一个 `S.stagePicked`：用户亲手点过就永久保留，直到 `stopLocalMedia()` 才复位。
- **e2e 里全屏几何断言别用 `window.innerWidth`**。headless 视口被 `--window-size=430,900`
  钉死，`innerWidth` 未必等于布局尺寸；要量「铺满整屏」就用
  `document.documentElement.clientWidth / clientHeight`。
- **`getBoundingClientRect().width` 含 `transform`**。`.hold-talk:active` 上有
  `transform: scale(.96)`，62px 会被量成 59.52 —— 按尺寸断言时必须留余量（用 `>= 56`），
  否则一条 CSS 动画就能让测试飘红。
- **点隐藏的 `<input type="file">` 不触发 `change`**。e2e 里给 `dt.files` 赋值后直接
  `click()` 是没用的（受信任事件才走默认行为），要 `dispatchEvent(new Event('change'))`。
- **信令抖 ≠ 通话断：`peer-left` 的宽限期必须按状态给。** 线上重连要走「退避 +
  WS 握手 + 重新注册」，远超 1.5 秒；而本地 `wrangler dev` 在同进程里几十毫秒就
  重连完 —— 于是 1.5 秒在本地永远够用、**线上必现误杀**：对方网络抖一下，我这边
  正在进行的通话被判死刑（`callKind` 清空、摄像头关掉、全屏界面退出）。
  现在通话态给到 20 秒（对齐产品对外承诺的重连窗口），聊天态保持 1.5 秒。
  更根本的理由：**WebRTC 媒体是端到端的**，信令断了媒体往往还活着，正在进行的
  通话不该因为一次信令抖动就被判死刑。⚠ **这个 bug 本地复现不了**，所以专门暴露
  `__rt.peerLeftGrace` 去断言「宽限期够不够长」，而不是靠「重连后通话还在不在」——
  后者在本地恒为真，等于没测。
- **「主动离开」不要蹭「抖动重连」的宽限期。** 顶栏 ✕ 退房时若正在通话，会先
  `endCall()` 发一条 `bye`（端到端、秒级到达），对端立刻收掉摄像头；
  `peer-left` 那条 20 秒宽限期只管「连不上的等待」。否则对方要对着一个已经空了
  的房间干瞪 20 秒。e2e 里把这条断言的等待卡在 **6 秒** —— 正是为了拦住
  「把主动离开也拖到宽限期上」这种回归。
- **别对空流调 `video.play()` —— 它返回的是一个永远 pending 的 promise。**
  接听流程上真栽过：为了让「未接听不泄露音视频」成立，推流被推迟到对方回
  `ring-answer` 之后；于是接听方那一刻 `<video>` 上绑的还是个**空 MediaStream**，
  `await play()` 一挂起，`ring-answer` 就发不出去，对面永远等不到 —— 双方互等成
  死锁。症状很有迷惑性：**B 的麦克风摄像头都开了（设备灯亮着），但两边都没进入
  通话态**。修法是 `ensureRemotePlayback()` 先看 `srcObject.getTracks().length`，
  没轨道就直接收工（轨道真到了 `ontrack` 会再调一次）。另外把「播放」挪到接听
  流程的**最后一步**：它只决定此刻看不看得见，不该挡住回执。

### 给开发的：`window.__rt`

页面加载后，控制台里有一个只读诊断对象 `window.__rt`（**不暴露口令**）：

```js

__rt.connectionState      // PC 连接状态
__rt.media                // 本端 音/视频 开关
__rt.remoteMedia          // 对端 音/视频 开关
__rt.audioBlocked         // 远端声音是否被自动播放策略挡住了
__rt.audioUnlockShown     // 解锁条是否正显示着
__rt.ringShown            // 是否正在响来电
__rt.callKind             // 通话类型：null = 不在通话 | 'audio' | 'video'
__rt.inCall               // 是否在通话中（等价 S.callKind !== null）
__rt.callRinging          // 是否还在「呼叫中」（对方尚未接听）
__rt.callLive             // 双方是否已真正接通（呼叫中、未接听时为 false）
__rt.ringGone             // 这颗来电是否已作废（对方挂断 / 超时）
__rt.callUiShown          // 全屏通话界面是否显示着
__rt.callMode             // 房间是否处于 call-mode（聊天外壳已收起）
__rt.callTimerText        // 通话时长文案，如 "01:23"
__rt.callPeerText         // 通话界面上「对方是谁」
__rt.callStateText        // 「正在呼叫… / 语音通话中 / 视频通话中」
__rt.peerLeftGrace        // 此刻「对方信令断开」多久才判定他真走了（通话中应为 20000）
__rt.composerHidden       // 输入栏是否被收起（通话中必须为 true，这是「点不到发起通话」的界面保证）
__rt.holdTalkBox          // 「按住说话」按钮的实测尺寸 { w, h, radius }
__rt.voiceCount           // 聊天气泡里的语音条数

__rt.txCount / __rt.rxCount   // 累计发出 / 收到 的传输条数
__rt.localTag / __rt.remoteTag // 视频窗口角标文案（含设备名与是否开麦）
__rt.facing               // 摄像头朝向：'user' 前置 / 'environment' 后置
__rt.camCount             // 探到的摄像头数量（>= 2 且视频通话中，才显示切换按钮）
__rt.flipShown            // 「切换前后摄像头」按钮当前可不可见
__rt.flipLog              // 最近一次切换的步骤轨迹（手机上切不动时报这个最快）
__rt.flip()               // 手动触发一次切换（等价于点那个 🔄）
__rt.refreshCams()        // 重新数一遍摄像头（去系统设置改过权限后，不用刷新页面）
__rt.stageMain            // 大窗是哪一格：'remote'（默认，对方铺满）| 'local'
__rt.stagePicked          // 用户是否亲手点过某一格（点过之后程序不再自动改布局）
__rt.stagePip             // 现在是不是「大窗 + 小窗」状态
__rt.smallPane            // 当前缩成小窗的是哪几格，默认 ['local']
__rt.selfTestLinks        // 首页两条自测外链的 href / target / rel
__rt.videoTuned           // 视频码率参数是否已生效
__rt.quality              // 我当前选的画质档位
__rt.remoteQuality        // 对方选的档位
await __rt.videoStats()   // 档位 / 码率上限 / 缩放 / 降级偏好 / 采集分辨率 / 实测 fps / 受限原因
__rt.__dropSocket()       // 模拟"连接已死"，验证重连
```

`videoStats().qualityLimitation` 是**把"卡"归因**的关键字段：

- `none` —— 没受限，卡顿来自网络丢包或对端
- `bandwidth` —— 带宽不够，降码率 / 降分辨率是正解
- `cpu` —— 编码算力不够，**降码率没用**，得降分辨率或帧率

没有这个字段，调码率全靠猜。

## 十一、为什么"必须 https"，以及怎么让手机不用手改地址

### 结论：http 下这个站点**完全不能用**，不是"凑合能用"

代码里有两处硬依赖，都**只在安全上下文**（https 或 localhost）才存在：

| 用在哪 | API | 非安全上下文下的表现 |
|---|---|---|
| 口令派生房间号 | `crypto.subtle` | `undefined`，`deriveRoomId()` 直接抛错 |
| 麦克风 / 摄像头 / 录音 | `navigator.mediaDevices` | `undefined`，语音视频通话全废 |

`public/app.js` 里有一道显式守卫（`onSubmitPassphrase` 开头）：非安全上下文直接提示
「当前地址不是安全上下文，浏览器不支持加密与音视频。请用 https:// 打开。」
所以**没有"退化成纯文字聊天"这条路** —— 连房间都进不去。

### 手机为什么默认走 http，桌面为什么不会

- **桌面**浏览器的地址栏有 HTTPS-First 行为：输入裸域名先试 https，通了就留在 https，
  用户根本看不到 http。
- 很多**手机**浏览器仍沿用「补全成 `http://` 再发请求」的老路子，第一条请求就是明文 http。
- **HSTS 救不了这一条**：规范要求浏览器**忽略 http 响应里的 `Strict-Transport-Security`**
  （Cloudflare 即使在 http 响应上带了那个头也没用）。HSTS 只能管"来过一次 https 之后"，
  管不了"第一次"。

### 修法：服务端在 http 上 301 到 https

`cloudflare/src/index.js` 的 `fetch()` 最前面做**协议 + 域名一次性归一**：只要求自边缘
且协议是 http，就 `301` 到 `https://简体裸域`。必须是 **301**（不是 302）—— 浏览器会把它
记下来，下次连试都不试 http。一次跳到位（https + 规范域名），不会出现两跳。

### ⚠ 判别"是不是在边缘"的坑（血泪）

不能靠 `url.hostname`，也不能靠 `cf-connecting-ip`：

- `wrangler dev` 会把请求**伪装成生产域名**（`wrangler.toml` 的 routes 绑了 `8.xn--fiqs8s`）。
  本地实测 `request.url` = `http://8.xn--fiqs8s/healthz`、`Host: 8.xn--fiqs8s`，**端口被抹掉**。
- 而且它会把 `cf-connecting-ip` 设成 `127.0.0.1`。

第一版就是栽在这上面：本地请求被当成"线上 http"，全部 301 到 `https://8.xn--fiqs8s`，
本地开发与 e2e 直接跑不起来。可靠信号只有**边缘才注入**的三个头 ——
`cf-ray` / `cf-visitor` / `x-forwarded-proto`（本地实测全为 null）。
**`cf-connecting-ip` 绝不能进这个判断。**

### 缺口与兜底

`run_worker_first = ["/", "/index.html"]`，所以这条规则覆盖的是**页面请求**
（用户在地址栏敲的那个就是）。静态资源本身直连 Assets、不走 Worker —— 但页面一旦被
跳到 https，它带出来的子资源自然也是 https，实际不会漏。

要在**边缘把所有路径（含静态资源）都兜住**，可在 Cloudflare 控制台里打开每个 zone 的
**SSL/TLS → Edge Certificates → Always Use HTTPS**。那是边缘动作，在 Worker 之前执行、
不用改代码 —— 本 Worker 里的 301 就是它的"版本化保险"：哪天开关被关掉，代码这层仍然生效。

> 官方 API 也能改：`PATCH /zones/{id}/settings/always_use_https`，但需要带
> `zone_settings:edit` 的令牌。wrangler 那份 OAuth 凭据权限不够，直连会报
> `10000 Authentication error` —— 别在这上面浪费时间，去控制台点两下更快。
